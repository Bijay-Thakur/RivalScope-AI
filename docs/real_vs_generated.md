# Real vs Generated — RivalScope Eval Data Map

This document explains **what the evaluation actually compares**, what counts as
test/original data, and what the pipeline retrieves/generates. Written from the
current harness in `backend/app/evaluation/` (Groq-judge smoke era).

---

## 1. Bottom line (read this first)

RivalScope eval is **not** a classic gold-answer QA benchmark.

| Question | Answer |
|---|---|
| Is there a gold competitor report we score against? | **No.** |
| Are `expected_facts` matched against retrieved text? | **No — unused by scorers today.** |
| What is the test set? | 22 company-pair tasks in `benchmark_tasks.json` (inputs + structural expectations). |
| What does research retrieve? | Live web via Tavily (search + page extract) when `RESEARCH_MODE=real`. |
| What does the LLM generate? | Comparison matrix + report sections from retrieved evidence. |
| What does grounding compare? | Each **evidence claim** vs its **cited source text** (same run). Reference-free faithfulness. |
| What does hallucination rate mean here? | Share of judged claims marked **unsupported** or **contradicted** by that source text (not wrong vs Wikipedia). |

So: **"original data" for grounding = the retrieved source page text itself.**
The claim is checked for support *by its own citation*, not by a separate human gold corpus.

## 2. Evaluation layers

### A. Structural / deterministic (no judge LLM)

Computed in every mode (`structural` and `full`). Compares **generated report shape**
against fields listed on the benchmark task:

| Metric | Original / expected (from task) | Generated / retrieved (from pipeline) | How scored |
|---|---|---|---|
| `task_completion` | Implicit checklist of major report fields | Report fields filled? | % major fields non-empty |
| `section_coverage` | `expected_sections` | Same-named report sections | % expected sections non-empty |
| `source_coverage` | `expected_source_types` | `report.sources[].source_type` | % expected types present |
| `citation_integrity` | (internal consistency only) | evidence.source_id in sources; URLs present | Structural integrity, not fact-check |
| `comparison_two_sidedness` | (none) | comparison matrix both sides filled | % rows with both sides |
| `comparison_citation_validity` | (none) | matrix source_ids resolve | % valid citation IDs |
| `overall_score` | weights in `scorers.score_report` | weighted combo of completion/sections/sources/citations/latency | Deterministic |

### B. Grounding / LLM-as-judge (`--mode full` only)

For each evidence item in the final report:

1. **Claim** = `evidence.claim` (usually title/snippet-derived from search)
2. **Source text** = `evidence.raw_text` (full-page extract) else `source.snippet`
3. Judge LLM (chain when `JUDGE_USE_GROQ=true`: Groq primary → Gemini fallback)
   returns `supported | partial | unsupported | contradicted` (or `error` / `citation_invalid`)

| Metric | Formula | Compared against gold facts? |
|---|---|---|
| `grounding_rate` | #supported / #judged_ok | **No** — vs cited source text |
| `hallucination_rate` | (#unsupported + #contradicted) / #judged_ok | **No** — unfaithful to citation |
| `comparison_grounding` | grounded matrix cells / judged cells | **No** — matrix cell vs joined snippets |

Empty source text → `citation_invalid` (no LLM call). Judge API failure → `error`
(rates become `null` if `n_judged_ok==0`, not silent 0.0).

### C. What is NOT evaluated (important gap)

- **`expected_facts` are loaded but never scored.** No string-match, no NLI vs gold facts.
- No human-labeled gold report.
- Eval JSON artifacts store **aggregate scores only**, not full claim↔source pairs.
  Per-claim judge I/O lives in runtime logs / LangSmith traces when tracing is on.

## 3. Pipeline data flow (real mode)

```
benchmark_tasks.json  →  ResearchRequest(our, competitor, market, report_type)
        ↓
LangGraph research_graph
  ├─ Tavily search_web (queries per track × company)
  ├─ Tavily extract_urls (top-N pages → raw_text)
  ├─ build evidence + sources
  ├─ fact_checker / comparison_agent / report_generator (LLMs)
        ↓
CompetitorReport { sections, evidence[], sources[], comparison_matrix }
        ↓
deterministic scorers  (+ judge on evidence claims if --mode full)
        ↓
eval_results/*.json|csv|md
```

**Retrieved by tools:** URLs, titles, snippets, full-page extracts from the live web.
**Generated by LLMs:** verified claims, comparison matrix cells, narrative report sections.
**Judged:** evidence claims against their own retrieved source text.

## 6. Example: what compared means for task-001

### Original / test-side (from dataset)

```
our_company = ClickUp
competitor  = Notion
market      = Project management and all-in-one workspace
report_type = sales_battlecard
expected_sections = company_snapshot, product_positioning, feature_comparison,
                    pricing_intelligence, recent_moves, strengths, weaknesses,
                    sales_battlecard, sources
expected_source_types = company_page, pricing_page, news, docs, other
expected_facts = [5 bullets — NOT used in score]
```

### Retrieved (runtime, not gold)

- Tavily results for queries like `ClickUp pricing plans official site`,
  `Notion latest news 2025 2026`, etc. (tracks: company_profile, product, pricing, news).
- Up to ~6000 chars `raw_text` per extracted page (`extract_max_chars`).
- Judge sees up to 2000 chars of that text (`_JUDGE_SOURCE_TEXT_MAX_CHARS`).

### Generated

- LLM writes report sections + comparison matrix from assembled context.
- Evidence claims are largely search-title/snippet derived, then carried into the report.

### Comparison performed

| Check | Left ("generated claim") | Right ("reference") |
|---|---|---|
| Section gate | report.company_snapshot filled? | expected_sections list |
| Source-type gate | report.sources types | expected_source_types |
| Grounding | evidence.claim | same-item retrieved source text |
| Fact accuracy vs expected_facts | — | **not implemented** |

## 7. If you want true "real vs generated" fact accuracy

Today you only have **faithfulness-to-citation**. To score accuracy vs known truths:

1. Treat `expected_facts` (or a richer gold set) as the reference.
2. Add a scorer: for each expected fact, search report/evidence/sources for support
   (string match, embedding, or NLI judge).
3. Persist per-claim judge records into `eval_results` (claim, url, verdict, rationale).

Until then, do **not** interpret grounding_rate as "how correct vs the real world" —
interpret it as "how often the cited page text supports the claim we attached to it."
